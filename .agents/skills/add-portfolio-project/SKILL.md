# ポートフォリオに作品を1つ追加する

## 合格率資料を扱う場合

第二種電気工事士の試験結果を掲載・更新するときは [2026年度の合格率資料](references/denko-pass-rates-2026.md) を読む。年度・期・人数・算式・公式出典・確認日を示し、全国の試験結果と講師の指導実績を区別する。最新値は掲載前に公式情報で再確認する。

## 最初に確認するもの

リポジトリ直下の `AGENTS.md` と `DESIGN.md` を読み、`git status --short` で既存の変更を確認する。現在の `index.html` の `#works`、`style.css` の `.lab-card` 関連、`server.cjs`、`.github/workflows/pages.yml` を確認する。パスはこのスキルのフォルダではなく、リポジトリ直下を基準とする。

作品名、短い説明、リンク先またはローカルの作品フォルダを、依頼内容や実ファイルから確認する。不明な公開先や作品の実績・機能を創作しない。必要な情報だけ質問し、確認できる作業は進める。

## 作品を配置する

- 既存の電工ラボを残し、`#works` 内へ新しい紹介カードを1つ追加する。既存作品を置き換えない。繰り返し実行時は同じ作品が追加済みでないか確認する。
- 複数作品になる場合、一覧の見出しやナビゲーション名を「プロジェクト作品」などに整え、各作品の名前は個別の見出しにする。`#works` のアンカーを維持し、見出しIDの重複を避ける。
- 既存の `.lab-card`、`.lab-art`、`.lab-copy`、`.eyebrow`、`.button` を再利用する。複数カード間の余白を追加する場合は既存デザインに合わせ、スタイルを無関係な領域へ適用しない。
- カードには作品名、何に使うかを伝える説明、確認できた主な機能、実際に開けるリンクを入れる。画像は提供されたものを使い、なければ既存の配色と文字で紹介面を作る。
- 生成り・深緑・淡い黄緑を基本にし、800px以下で縦積みにする。キーボードフォーカス、画像の代替テキスト、適切な見出しを保つ。

## 作品へのリンクと配信

### すでに外部公開されている作品

提供・確認されたURLへリンクする。リンク追加だけなら、ローカルサーバーや公開ワークフローの変更は不要。新しいタブで開く場合は `rel="noopener noreferrer"` を付ける。

### リポジトリ内で公開する作品

- このサイトはGitHub Pagesの静的サイト。HTML・CSS・JavaScriptなど静的配信で動くか確認する。サーバー処理が必要なら、静的コピーで動くと判断せず、別の公開先など必要な対応を説明する。
- 配信用フォルダを重複しない短い名前で用意する。既存の電工ラボは `denko/`。依存する画像・データなども含める。
- 元の作品フォルダが独立したGitリポジトリの場合、`.git`を含めず公開に必要な成果物だけをコピーする。登録されない入れ子のファイルや未設定のサブモジュールをそのまま参照しない。
- プロジェクトサイトの公開パスは `/sato_port1/`。リンクは `作品フォルダ/` などの相対パスとし、サイトルートを指す `/作品フォルダ/` を安易に使わない。作品側にもポートフォリオへ戻る相対リンクを用意する。
- `.github/workflows/pages.yml` の「Prepare static site」に、作品の配信ファイルを `_site/作品フォルダ/` へコピーする処理を追加する。現在の処理はトップページと `denko/` だけをコピーするため、フォルダを置くだけでは公開されない。
- `server.cjs` は許可するファイルを列挙している。ローカル確認用に作品ページとCSS・JS・画像など必要なルートを追加する。全リポジトリを無制限に配信する変更は避ける。
- `DESIGN.md` のページ構成・部品に変更を反映し、`README.md` に作品の編集場所と必要な起動手順を追記する。

## 確認と完了

- `git diff --check` と、変更したJavaScriptの `node --check <ファイル>` を実行する。
- 差分と `git status` を確認し、カードが1件だけ追加され、既存作品と相対リンクが維持されていることを確認する。配信用ファイルが親リポジトリの `git ls-files` に含まれるかも確認する。
- プレビューが利用できる場合、通常幅と800px以下の幅で見出し・カード・リンクを確認し、新しい作品を開いて戻れること、必要なアセットを取得できることを確認する。利用できない検証は完了したと報告しない。
- コミット・push・公開は現在のユーザー依頼と既存の許可範囲に従う。このスキルを作成・使用すること自体を、追加の公開許可と解釈しない。コミット対象は今回の変更ファイルだけを明示する。
- 公開する場合、既存の `origin` とブランチを確認し、push後は対象コミットのActions実行が成功するまで確認する。失敗時はログに基づいて修正し、権限や認証が原因なら具体的な障害を伝える。
- 最後に作品名、変更ファイル、確認結果、コミット・pushの有無、公開できた場合はURLを伝える。
